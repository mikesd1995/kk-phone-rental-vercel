# LINE booking test admission — source controls, 2026-11-15

Evidence class: `LOCAL_MOCK`. This change adds an optional identity admission boundary to existing webhook and customer authentication entrypoints. It does not enable the booking feature or select/provision an acceptance target.

`KK_LINE_BOOKING_TEST_MODE` absent or literal `false` preserves existing admission. Literal `true` requires `KK_LINE_BOOKING_TEST_USER_IDS`: 1–10 distinct exact `U[0-9a-f]{32}` user IDs separated by commas. Surrounding token whitespace is trimmed. Other present mode values, missing/empty/malformed/duplicate/oversized lists fail with the safe `LINE_BOOKING_TEST_CONFIG_INVALID` code. Configuration and identity values are never included in that error.

After valid signature and JSON checks, the signed webhook validates configuration and requires both the configured owner identity and effective owner push target to be allowlisted private user IDs. It filters events before Inbox profile/media/persistence, booking snapshot resolution, consent lookup, replies and owner decisions. Denied events receive HTTP 200; invalid configuration receives HTTP 503. Mixed batches admit only allowed private-user events. Direct `processEvent` and `processOwnerPostback` entrypoints apply the same admission before work. Existing owner identity/signature and durable canonical claim checks remain in force.

The customer auth runtime validates configuration before provider/store requests. OAuth callbacks must first verify the provider identity; denied identities then clear cookies and receive HTTP 403 before a session can be created. Existing sessions require one stored-identity discovery read before membership is knowable. Denied session/accept/logout calls clear the session cookie and cannot read Terms, accept Terms or revoke a session. Session GET returns the existing guest shape; accept/logout return a safe denial. Existing CSRF checks still precede POST work. Test-mode logout adds identity discovery; absent/false keeps its original behavior.
